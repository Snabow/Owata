## Goal

Implement the smallest single-worker execution loop that can take one durable OWATA work item from queue to verified completion without Human intervention.

```text
QUEUED → claim → begin attempt → resolve spec → execute → verify
  → if FAIL: bounded automatic repair (linked to FAIL attempt) → execute → verify
  → COMPLETED only when latest attempt is execution_ok AND verification PASS
  → else terminal FAILED when no defined repair path / budget exhausted / setup or repair error
```

---

## Success condition

> One queued work item can be executed, fail verification at least once, be automatically repaired, and subsequently reach verified COMPLETED state without Human interaction.

Uses production worker-loop code and WP-001 durable Control Core.

---

## Durable contract

### Attempt outcomes

| Outcome | Meaning |
| --- | --- |
| `PASS` | `execution_ok` and verification PASS (combined gate) |
| `FAIL` | Finished execute/verify path; overall gate failed (includes false+PASS) |
| `SETUP_ERROR` | Spec/handler preparation failed before execute |
| `EXEC_ERROR` | `execute` threw |
| `VERIFY_ERROR` | `verify` threw |
| `RESULT_ERROR` | Execution occurred but result could not be durably represented |
| `ABANDONED` | Ownership ended before final classification |

### Event semantics

Attempt lifecycle (`work.attempt_started` / `work.attempt_finished`) is distinct from task execution lifecycle (`work.execution_started` / `work.execution_finished`). SETUP_ERROR never claims execution started or finished.

Authoritative order uses durable `event_seq` (identity remains `event_id`; timestamps are observational). SQLite `listEvents()` and JSONL projection share the same `event_seq` order.

### Completion

`completeWork` uses the latest attempt by `attempt_number` (finished or not). That attempt must be finished with `execution_ok`, verification PASS, and `attempt_outcome` PASS. Older PASS never authorizes completion.

### Terminal failure

Work state `FAILED` is terminal: not claimable, not requeued, lease cleared, durable `failure_reason`. Covers repair-budget exhaustion, non-repairable outcomes, `repair()` exceptions, and setup failures.

### Repair

Automatic repair is gated to one specific finished verification-FAIL attempt. Obtaining, validating, and applying the repair result is a single exception boundary: non-fencing failures terminalize as FAILED without incrementing `repair_count`. `STALE_LEASE` is never swallowed.

### Schema

Exact migration chain only (fresh / v1→v2→v3→v4). Unknown version 0 and future versions fail explicitly.

## Scope

- Single worker claiming via WP-001 leases / fencing
- Durable execution spec (`task_type` + JSON input) on work items
- Durable attempt/result history and outcomes
- Verification gate distinct from execution
- Bounded automatic repair (deterministic, no LLM) with attempt provenance
- Terminal FAILED when repair path exhausted or non-repairable errors
- Crash/restart recovery using WP-001 lease recovery + ABANDONED classification
- Deterministic local proving sample

## Proving sample

Task type `sum_two`:

1. Attempt 1 executes with intentional defect → verification FAIL
2. Automatic repair clears the defect in durable input (linked to attempt 1)
3. Attempt 2 executes correctly → verification PASS → COMPLETED

Repair must change the failing cause; it must not force the verifier to PASS.

## Acceptance criteria (summary)

- Completion requires latest-attempt combined gate (execution_ok AND verification PASS AND outcome PASS)
- Exceptions, setup errors, and abandoned attempts are durably classified
- Repair budget exhaustion / repair throw / setup error → FAILED (no infinite re-execution)
- Repair linked to specific FAIL attempt; ordering gates enforced
- Schema version gates reject unknown/future versions
- Real process-interruption recovery tested with same `work_id`
- Stale lease fencing remains effective
- WP-000 / WP-001 regressions remain green
- Branch committed and pushed (not merged)
