## Goal

Implement the smallest single-worker execution loop that can take one durable OWATA work item from queue to verified completion without Human intervention.

```text
QUEUED → claim → execute → capture result → verify
  → if FAIL: bounded automatic repair (linked to FAIL attempt) → execute → verify
  → COMPLETED only when execution_ok AND verification PASS
  → else terminal FAILED when no defined repair path / budget exhausted
```

---

## Success condition

> One queued work item can be executed, fail verification at least once, be automatically repaired, and subsequently reach verified COMPLETED state without Human interaction.

Uses production worker-loop code and WP-001 durable Control Core.

---

## Durable contract (R1)

### Completion

`COMPLETED` requires both `execution_ok === true` and `verification_status === PASS`. Verifier PASS never overrides unsuccessful execution.

### Attempt classification

Every started attempt is eventually durable as PASS, FAIL, EXEC_ERROR, VERIFY_ERROR, or ABANDONED (lease/process ended before finalization). Crash/unknown is not mislabeled as definite execution failure.

### Terminal failure

Work state `FAILED` is terminal: not claimable, not requeued by lease recovery, lease cleared, durable `failure_reason` + `work.failed` evidence.

### Repair

Automatic repair is gated to one specific finished verification-FAIL attempt (`attempt_id`), with `repair_applied` / event linkage. ERROR/ABANDONED/PASS cannot trigger repair.

### Schema

Exact migration chain only (fresh / v1→v2→v3). Unknown version 0 and future versions fail explicitly.

## Proving sample

Task type `sum_two`:

1. Attempt 1 executes with intentional defect → verification FAIL
2. Automatic repair clears the defect in durable input (linked to attempt 1)
3. Attempt 2 executes correctly → verification PASS → COMPLETED

Repair must change the failing cause; it must not force the verifier to PASS.

---

## Acceptance criteria (summary)

- Completion requires execution_ok AND verification PASS
- Exceptions and abandoned attempts are durably classified
- Repair budget exhaustion / non-repairable errors → FAILED (no infinite re-execution)
- Repair linked to specific FAIL attempt; ordering gates enforced
- Schema version gates reject unknown/future versions
- Real process-interruption recovery tested with same `work_id`
- Stale lease fencing remains effective
- WP-000 / WP-001 regressions remain green
- Branch committed and pushed (not merged)
